- Hazm's diacritics removal is too narrow for Quranic text and would leave thousands of marks behind.
   DIACRITICS_PATTERNS = [(r'[ًٌٍَُِّْ]', '')] — only U+064B-U+0652. It does NOT remove U+0670 superscript alef (3,330 occurrences in this file), U+0640 tatweel (939), or Quranic annotation signs U+06D6-U+06ED (4,551+). Also its default digit direction (ASCII -> Persian) is wrong for building a canonical search index, which should key on ASCII digits.
   src: https://raw.githubusercontent.com/roshan-research/hazm/master/hazm/constants.py | 2026-10-31 | high
- Parsivar 0.2.3.1 normalizes in the opposite digit direction and applies Persian-specific letter folding that is destructive to Arabic Quran text.
   PyPI: parsivar 0.2.3.1, released 2024-01-02, MIT. normalizer.py maps Persian AND Arabic-Indic digits to ASCII (۰|٠ -> 0 ... ۹|٩ -> 9), maps alef variants ٲ|ٱ|إ|ﺍ|أ -> ا, ك/ڪ/ﻚ -> ک, ى|ي|ﻯ|ﻱ -> ی, and ة|ہ|ھ|ﻩ|ۀ|ە -> ه, strips tatweel U+0640 plus the six basic harakat, and converts '¬' (U+00AC) to ZWNJ U+200C. Applying this to the Arabic corpus would collapse teh marbuta into heh and alef-maqsura into yeh before indexing — acceptable only as a deliberate recall-oriented search fold, never to the displayed Quran text.

- ZWNJ (U+200C) is Persian-only and must be handled asymmetrically: inserted/kept in Persian queries, stripped before matching Arabic.
   Hazm's normalizer joins token pairs with an explicit ZWNJ character and rewrites the verb prefix with re.sub(r'^(ن?می)', r'\1‌', ...), turning 'میکنم' into 'می‌کنم'. Parsivar maps the typographic not-sign '¬' to U+200C. The Quran file contains 0 ZWNJ, so any ZWNJ surviving from a Persian query ('کتاب‌ها', 'می‌خواهد') must be deleted (or treated as a word separator) before comparing with Arabic tokens; otherwise exact-match recall is zero for those terms.

- quran-search-engine (MIT, TypeScript) has the most complete modern normalization regex, but its final character filter deletes Persian letters and cannot be applied to Persian queries.

- A practical root-search architecture is: morphology map from Buckwalter root to every surface word, plus a lemma map, with query-time root expansion.
   quran-search-engine's API takes quranData + morphologyMap + wordMap and exposes search(query, data, morphologyMap, wordMap, {lemma:true, root:true, semantic:true}). Its English-Arabic guide shows the non-Arabic path needs a hand-built concept map, e.g. {english:['truth','verity','trueness','accuracy'], arabic:['حق','صدق']} — stored as roots only, then root expansion finds 'الحق','بالحق','حقا','صدق','صدقا','بالصدق'. Without such a map, an English or Persian query cannot reach Arabic roots; this is where an LLM translation step (EN/FA -> Arabic search terms) belongs, not in answer generation.
   src: https://raw.githubusercontent.com/adelpro/quran-search-engine/main/docs/guides/english-arabic-search.md, https://raw.githubusercontent.com/adelpro/quran-search-engine/main/src/utils/normalization.ts | 2026-10-31 | high
- Corpus morphology tags use Buckwalter ASCII transliteration, not Arabic script, so a conversion table is required before display or matching.
   Observed ROOT:/LEM: values are strings such as $Am, $An, $Eb, $El, $Er, $HH, $Hm and lemmas such as $a>on, $aAEir, $aA^'a. Buckwalter maps '>' to hamza, '$' to shin, 'E' to ayn, etc. Build a BW->Arabic table (and its inverse) or reuse an existing pyarabic/quranic-corpus converter; otherwise root keys will never match an Arabic-script query.
   src: https://raw.githubusercontent.com/cltk/arabic_morphology_quranic-corpus/master/quranic-corpus-morphology-0.4.txt | 2026-10-31 | high
- Quran typography requires dedicated Quranic fonts and generous line-height; Vazirmatn is the standard Persian UI face, but exact font metrics were not live-verified in this session.
   Standard choices: Amiri Quran (SIL OFL 1.1, designed for Quranic text with full harakat), KFGQPC Uthmanic Hafs (King Fahd Complex Uthmanic script, the glyph set matching Medina-Mushaf orthography), and Vazirmatn (SIL OFL 1.1) for Persian UI strings. Practical rules: set line-height >= 1.8-2.0 for fully vowelled Arabic so stacked marks (shadda+fatha, superscript alef) do not clip; use font-display: swap; subset to Arabic + Latin; avoid letter-spacing (breaks Arabic joining); set dir='rtl' and lang='fa'/'ar' per element. Treat these font license/metric claims as LOW confidence — WebSearch/WebFetch were intermittently returning 502 and I could not fetch the font repos before this output.

CAVEATS: Coverage gaps and things that would change the answer: (1) Persian LLM quality evidence for 2026 — I did NOT obtain live benchmark numbers (ParsBench/PersianBench or vendor evals); any model recommendation must be re-verified with a human-eval set of ~50 Persian religious questions. Known risk to test: Arabic-script tokenization inflates token counts and can truncate prompts, and mixed RTL/LTR prompts can cause bidi ordering artifacts in streamed output. (2) RTL font performance (WOFF2 file sizes, harakat rendering on low-end Android) was not measured; the font finding is flagged low confidence with no sources. (3) The repo file's provenance is unknown: it is named quran-simple.txt but contains full diacritics including U+0640+U+0670 sequences typical of Tanzil's enhanced/Uthmani-family texts, not Tanzil 'Simple'; re-download the intended Tanzil type and checksum it. (4) Root count differs by method: 1,642 distinct ROOT strings counted from v0.4 vs commonly cited 1,651 roots on corpus.quran.com — confirm which the site uses before publishing a number. (5) Quranic Arabic Corpus licensing (GPL + 'CHANGING IT IS NOT ALLOWED') likely conflicts with redistributing a modified morphology index; legal review needed. (6) WebSearch returned malformed results and WebFetch intermittently 502'd; only URLs listed in findings were successfully fetched. (7) Hazm/Parsivar are Persian-text tools; no single library covers both Persian normalization and Quranic Arabic normalization — the pipeline must be two-stage and language-detected first.
PICK: Build the retrieval layer on quran-search-engine (MIT, TypeScript, 38 stars, pushed 2026-10-07) for its tokenizer/normalization and root/lemma search, fed by a normalized static index built from Tanzil 'Simple Clean' (search copy) + Tanzil Uthmani/enhanced (display copy) + Quranic Arabic Corpus v0.4 morphology (subject to its GPL/no-modification license). Run Persian queries through Hazm 0.12.1 (MIT) with a custom pre-pass that strips ZWNJ and maps Persian digits, then a Quran-specific Arabic normalizer (strip U+064B-U+065F, U+0670, U+0640, U+06D6-U+06ED; fold أإآٱ->ا, ة->ه, ى->ي for the index only). Runner-up: Alfanous (LGPL-3.0, 285 stars) as a drop-in Arabic Quran search backend if you want a Python server rather than a TS library; its normalizer is the cleanest reference implementation but LGPL obligations apply. Avoid applying Parsivar/Hazm defaults or quran-search-engine's final [ء-ي] filter to Persian input — both destroy Persian letters.

- A fatwa is a legal ruling by a qualified mufti in response to a specific question and is generally non-binding in Sunni Islam, while tafsir is Quranic exegesis by a mufassir.
   Fatwa: "legal ruling on a point of Islamic law (sharia) delivered by a qualified legal scholar, called a mufti, in answer to a specific question from an individual, judge, or government body"; normally nonbinding unless issued by a government judge in an Islamic state (Shia marja' rulings are treated as binding by followers). Tafsir: "exegesis, or commentary, of the Quran"; author is a mufassir; attempts to provide explanation, interpretation, context or commentary. Implication: an AI answer must never be labelled a fatwa, and even a tafsir excerpt is a named scholar's interpretation, not the Quran's own voice.
   src: https://en.wikipedia.org/wiki/Fatwa, https://en.wikipedia.org/wiki/Tafsir | 2026-10-31 | medium

EXACT ANSWER CONTRACT (JSON fields):
1. request_id: string
2. lang: "en" | "fa"
3. intent: "quran_topic" | "fiqh" | "history" | "personal_guidance" | "off_topic" | "no_retrieval"
4. status: "answered" | "answered_with_boundary" | "refused_off_topic" | "refused_no_retrieval"
5. verses[]: each { surah:int, ayah:int, surah_name_en, surah_name_fa, arabic_tanzil:string (unmodified quran-simple.txt), translations:[{edition_id, translator, language:"en"|"fa", text, license}], context:{ayah_before, ayah_after}, tafsir:[{work_id, work_title, author, translator, language, excerpt, publisher_url}] (optional; only published, attributed works) }
6. citation: { quran_com_url:"https://quran.com/{surah}/{ayah}", tanzil_url:"https://tanzil.net/#{surah}:{ayah}" }
7. disclosure: { arabic_source:"Tanzil quran-simple.txt (Hafs)", translation_not_quran:true, tafsir_is_interpretation:true, not_a_fatwa:true }
8. actions: ["copy_arabic","copy_translation","share_card"]
9. audit: { retrieval_score:float, matched_terms:string[] }
10. generated_commentary: false

UI RULES: Arabic first, then the translation directly beneath with a visible translator label ("Translation: Saheeh International — translation is interpretation, not the Quran"). Second translation collapsed by default; all translations selectable. Tafsir collapsed and labelled by author/work ("Ibn Kathir, Abridged — scholarly interpretation, not a fatwa"). Context panel shows the previous and next ayah. English defaults: Saheeh International (quran.com id 20) primary, M.A.S. Abdel Haleem secondary. Persian defaults: الهی قمشه‌ای (fa.ghomshei) primary, مکارم شیرازی (fa.makarem) secondary; selector exposes all 13 Tanzil Persian editions. Persian UI: RTL, Persian digits, Vazirmatn-style font; Arabic verse visually distinct from Persian translation. No transliteration in the Persian UI; optional in English. NEVER machine-translate a verse at runtime.

INTENT HANDLING:
- quran_topic -> answer with Verse Cards.
- fiqh/legal ("is X haram?") -> status "answered_with_boundary": show only relevant verses, never a ruling; fixed boundary text. Do not infer halal/haram.
- history -> answer only if Quranic verses retrieved; otherwise state the Quran does not provide the detail and point to tafsir/seerah; do not invent.
- personal_guidance -> verses plus open reflection prompts, never counselling or rulings.
- off_topic -> refuse.
- no relevant verse above retrieval threshold -> refuse; never answer from model memory.

REFUSAL COPY (exact):
Off-topic, EN: "I can only answer questions about the Quran. This question is outside that scope, so I cannot answer it."
Off-topic, FA: «من فقط به پرسش‌هایی درباره قرآن پاسخ می‌دهم. این پرسش خارج از این حوزه است و نمی‌توانم به آن پاسخ دهم.»
No retrieval, EN: "I could not find a Quranic verse relevant to this question, so I cannot answer it. Try rephrasing with Quranic terms, or consult a qualified scholar."
No retrieval, FA: «هیچ آیه‌ای از قرآن مرتبط با این پرسش پیدا نکردم؛ بنابراین نمی‌توانم به آن پاسخ دهم. لطفاً پرسش را با واژه‌های قرآنی بازنویسی کنید یا با عالمی واجد شرایط مشورت کنید.»
Fiqh boundary, EN: "The Quran addresses this topic, but a ruling (fatwa) requires a qualified mufti. The relevant verses are shown below; this is not a fatwa."
Fiqh boundary, FA: «قرآن درباره این موضوع آیاتی دارد، اما صدور حکم شرعی (فتوا) فقط از سوی مفتی واجد شرایط ممکن است. آیات مرتبط در ادامه آمده است؛ این پاسخ فتوا نیست.»
Sensitive-verse standing note, EN: "Read in context: the full verse and adjacent verses are shown. Translations and interpretations differ; only the Arabic Quranic text is authoritative."
Sensitive-verse note, FA: «در بافت بخوانید: آیه کامل و آیات مجاور نمایش داده شده است. ترجمه‌ها و تفسیرها متفاوت‌اند؛ تنها متن عربی قرآن مرجع است.»

SENSITIVE TOPICS: always render the complete verse (never a truncated clause), include one ayah before and after, show at least two translations where available, and offer tafsir excerpts from at least two named works when available. Do not add editorial framing, apologies, or "this verse is often misused" commentary generated by AI; instead a neutral fixed context panel with surah, revelation place/period, and adjacent verses. Never label a verse as violent/controversial in the UI taxonomy; index by surah/ayah and topic only. This satisfies Quran Foundation's terms that snippets preserve original context and meaning, and avoids the "conjecture" Dar al-Ifta warned against.
